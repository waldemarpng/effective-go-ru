# Пустой идентификатор

[оригинал](https://go.dev/doc/effective_go#blank)

Мы уже пару раз упоминали пустой идентификатор — в контексте циклов `for` `range` и map. Пустому идентификатору можно присвоить или объявить с ним значение любого типа; значение безопасно отбрасывается. Это немного как запись в Unix‑файл `/dev/null`: это значение только для записи, заполнитель там, где переменная нужна, а само значение неважно. У него есть применения сверх тех, что мы уже видели.

## Пустой идентификатор в множественном присваивании

[оригинал](https://go.dev/doc/effective_go#blank_assign)

Использование пустого идентификатора в цикле `for` `range` — частный случай общей ситуации: множественного присваивания.

Если присваивание требует нескольких значений слева, но одно из них программа не использует, пустой идентификатор слева избавляет от нужды создавать фиктивную переменную и ясно показывает, что значение отбрасывается. Например, вызывая функцию, которая возвращает значение и ошибку, когда важна только ошибка, отбросьте ненужное значение пустым идентификатором.

```
if _, err := os.Stat(path); os.IsNotExist(err) {
    fmt.Printf("%s does not exist\n", path)
}
```

Иногда встречается код, который отбрасывает значение ошибки, чтобы её игнорировать; это ужасная практика. Всегда проверяйте возвраты ошибок: их дают не просто так.

```
// Bad! This code will crash if path does not exist.
fi, _ := os.Stat(path)
if fi.IsDir() {
    fmt.Printf("%s is a directory\n", path)
}
```

## Неиспользованные импорты и переменные

[оригинал](https://go.dev/doc/effective_go#blank_unused)

Ошибка — импортировать пакет или объявить переменную и не использовать их. Неиспользованные импорты раздувают программу и замедляют компиляцию, а переменная, которую инициализировали и не использовали, как минимум зря потраченное вычисление и, возможно, признак большей ошибки. Однако когда программа в активной разработке, неиспользованные импорты и переменные возникают часто, и раздражает удалять их только чтобы компиляция прошла, а потом снова они понадобятся. Пустой идентификатор даёт обходной путь.

Эта недописанная программа имеет два неиспользованных импорта (`fmt` и `io`) и неиспользованную переменную (`fd`), поэтому не скомпилируется, но хотелось бы проверить, верен ли уже написанный код.

```
package main

import (
    "fmt"
    "io"
    "log"
    "os"
)

func main() {
    fd, err := os.Open("test.go")
    if err != nil {
        log.Fatal(err)
    }
    // TODO: use fd.
}
```

Чтобы заглушить жалобы на неиспользованные импорты, обратитесь пустым идентификатором к символу из импортированного пакета. Аналогично, присваивание неиспользованной переменной `fd` пустому идентификатору заглушит ошибку неиспользованной переменной. Эта версия программы компилируется.

```
package main

import (
    "fmt"
    "io"
    "log"
    "os"
)

var _ = fmt.Printf // For debugging; delete when done.
var _ io.Reader    // For debugging; delete when done.

func main() {
    fd, err := os.Open("test.go")
    if err != nil {
        log.Fatal(err)
    }
    // TODO: use fd.
    _ = fd
}
```

По соглашению глобальные объявления, глушащие ошибки импорта, должны стоять сразу после импортов и быть с комментарием — и чтобы их было легко найти, и как напоминание потом прибрать.

## Импорт ради побочного эффекта

[оригинал](https://go.dev/doc/effective_go#blank_import)

Неиспользованный импорт вроде `fmt` или `io` в предыдущем примере в итоге нужно использовать или убрать: присваивания пустому идентификатору помечают код как работу в процессе. Но иногда полезно импортировать пакет только ради побочных эффектов, без явного использования. Например, во время своей функции `init` пакет `net/http/pprof` регистрирует HTTP‑обработчики, которые дают отладочную информацию. У него есть экспортируемый API, но большинству клиентов нужна только регистрация обработчиков, а данные они смотрят через веб‑страницу. Чтобы импортировать пакет только ради побочных эффектов, переименуйте пакет в пустой идентификатор:

```
import _ "net/http/pprof"
```

Эта форма импорта ясно показывает, что пакет импортируют ради побочных эффектов, потому что другого возможного использования пакета нет: в этом файле у него нет имени. (Если бы имя было и мы его не использовали, компилятор отверг бы программу.)

## Проверки интерфейсов

[оригинал](https://go.dev/doc/effective_go#blank_implements)

Как мы видели в обсуждении интерфейсов выше, тип не обязан явно объявлять, что реализует интерфейс. Вместо этого тип реализует интерфейс просто тем, что реализует методы интерфейса. На практике большинство преобразований интерфейсов статичны и поэтому проверяются во время компиляции. Например, передача `*os.File` в функцию, ожидающую `io.Reader`, не скомпилируется, если `*os.File` не реализует интерфейс `io.Reader`.

Некоторые проверки интерфейсов всё же происходят во время выполнения. Один случай — в пакете `encoding/json`, который определяет интерфейс `Marshaler`. Когда JSON‑кодировщик получает значение, реализующее этот интерфейс, он вызывает метод маршалинга значения, чтобы преобразовать его в JSON, вместо стандартного преобразования. Кодировщик проверяет это свойство во время выполнения утверждением типа вроде:

```
m, ok := val.(json.Marshaler)
```

Если нужно только спросить, реализует ли тип интерфейс, не используя сам интерфейс, возможно как часть проверки ошибки, используйте пустой идентификатор, чтобы игнорировать значение утверждения типа:

```
if _, ok := val.(json.Marshaler); ok {
    fmt.Printf("value %v of type %T implements json.Marshaler\n", val, val)
}
```

Такая ситуация возникает, когда внутри пакета, реализующего тип, нужно гарантировать, что тип действительно удовлетворяет интерфейсу. Если тип — например, `json.RawMessage` — нуждается в своём JSON‑представлении, он должен реализовать `json.Marshaler`, но нет статических преобразований, которые заставили бы компилятор проверить это автоматически. Если тип по недосмотру не удовлетворит интерфейс, JSON‑кодировщик всё равно будет работать, но не использует свою реализацию. Чтобы гарантировать корректность реализации, в пакете можно использовать глобальное объявление с пустым идентификатором:

```
var _ json.Marshaler = (*RawMessage)(nil)
```

В этом объявлении присваивание с преобразованием `*RawMessage` к `Marshaler` требует, чтобы `*RawMessage` реализовывал `Marshaler`, и это свойство проверят во время компиляции. Если интерфейс `json.Marshaler` изменится, этот пакет больше не скомпилируется, и мы будем знать, что его нужно обновить.

Появление пустого идентификатора в этой конструкции показывает, что объявление существует только для проверки типа, а не чтобы создать переменную. Не делайте так для каждого типа, который удовлетворяет интерфейсу. По соглашению такие объявления используют только когда в коде нет статических преобразований, а это редкость.
