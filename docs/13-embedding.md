# Встраивание

[оригинал](https://go.dev/doc/effective_go#embedding)

Go не даёт обычного, управляемого типами понятия подклассов, но умеет «одалживать» части реализации, встраивая типы в структуру или интерфейс.

Встраивание интерфейсов очень просто. Мы уже упоминали интерфейсы `io.Reader` и `io.Writer`; вот их определения.

```
type Reader interface {
    Read(p []byte) (n int, err error)
}

type Writer interface {
    Write(p []byte) (n int, err error)
}
```

Пакет `io` также экспортирует несколько других интерфейсов, которые задают объекты, способные реализовать несколько таких методов. Например, есть `io.ReadWriter` — интерфейс, содержащий и `Read`, и `Write`. Можно задать `io.ReadWriter`, явно перечислив два метода, но проще и выразительнее встроить два интерфейса, чтобы получить новый, вот так:

```
// ReadWriter is the interface that combines the Reader and Writer interfaces.
type ReadWriter interface {
    Reader
    Writer
}
```

Это говорит ровно то, на что похоже: `ReadWriter` умеет то, что умеет `Reader`, и то, что умеет `Writer`; это объединение встроенных интерфейсов. В интерфейсы можно встраивать только интерфейсы.

Та же базовая идея применима к структурам, но с более далёкими следствиями. В пакете `bufio` есть два структурных типа, `bufio.Reader` и `bufio.Writer`, каждый из которых, разумеется, реализует аналогичные интерфейсы из пакета `io`. И `bufio` также реализует буферизованный reader/writer: объединяет reader и writer в одну структуру через встраивание — перечисляет типы внутри структуры, но не даёт им имён полей.

```
// ReadWriter stores pointers to a Reader and a Writer.
// It implements io.ReadWriter.
type ReadWriter struct {
    *Reader  // *bufio.Reader
    *Writer  // *bufio.Writer
}
```

Встроенные элементы — указатели на структуры и, конечно, должны быть инициализированы так, чтобы указывать на настоящие структуры, прежде чем их можно использовать. Структуру `ReadWriter` можно было бы написать как

```
type ReadWriter struct {
    reader *Reader
    writer *Writer
}
```

но тогда чтобы продвинуть методы полей и удовлетворить интерфейсы `io`, пришлось бы ещё дать перенаправляющие методы, вот так:

```
func (rw *ReadWriter) Read(p []byte) (n int, err error) {
    return rw.reader.Read(p)
}
```

Встраивая структуры напрямую, мы избегаем этой бухгалтерии. Методы встроенных типов прилагаются бесплатно, а значит `bufio.ReadWriter` не только имеет методы `bufio.Reader` и `bufio.Writer`, но и удовлетворяет всем трём интерфейсам: `io.Reader`, `io.Writer` и `io.ReadWriter`.

Есть важный способ, которым встраивание отличается от наследования. Когда мы встраиваем тип, методы этого типа становятся методами внешнего типа, но когда их вызывают, получатель метода — внутренний тип, а не внешний. В нашем примере вызов метода `Read` у `bufio.ReadWriter` имеет ровно тот же эффект, что выписанный выше перенаправляющий метод; получатель — поле `reader` у `ReadWriter`, а не сам `ReadWriter`.

Встраивание может быть и просто удобством. Этот пример показывает встроенное поле рядом с обычным именованным.

```
type Job struct {
    Command string
    *log.Logger
}
```

Тип `Job` теперь имеет `Print`, `Printf`, `Println` и другие методы `*log.Logger`. Конечно, можно было дать `Logger` имя поля, но это не обязательно. И теперь, после инициализации, можно логировать в `Job`:

```
job.Println("starting now...")
```

`Logger` — обычное поле структуры `Job`, так что инициализировать его можно обычным способом внутри конструктора `Job`, вот так,

```
func NewJob(command string, logger *log.Logger) *Job {
    return &Job{command, logger}
}
```

или составным литералом,

```
job := &Job{command, log.New(os.Stderr, "Job: ", log.Ldate)}
```

Если нужно обратиться к встроенному полю напрямую, имя типа поля, без квалификатора пакета, служит именем поля, как в методе `Read` нашей структуры `ReadWriter`. Здесь, если нужно получить `*log.Logger` переменной `job` типа `Job`, мы напишем `job.Logger`, что полезно, если хотим уточнить методы `Logger`.

```
func (job *Job) Printf(format string, args ...interface{}) {
    job.Logger.Printf("%q: %s", job.Command, fmt.Sprintf(format, args...))
}
```

Встраивание типов ставит проблему конфликтов имён, но правила их разрешения простые. Во‑первых, поле или метод `X` скрывает любой другой элемент `X` в более глубоко вложенной части типа. Если бы в `log.Logger` было поле или метод `Command`, поле `Command` у `Job` его затмило бы.

Во‑вторых, если одно и то же имя появляется на одном уровне вложенности, это обычно ошибка; было бы ошибочно встраивать `log.Logger`, если в структуре `Job` уже есть другое поле или метод `Logger`. Однако если дублирующее имя никогда не упоминается в программе вне определения типа, это нормально. Эта оговорка даёт некоторую защиту от изменений во встроенных извне типах: нет проблемы, если добавят поле, конфликтующее с другим полем в другом подтипе, если ни одно поле никогда не используется.
