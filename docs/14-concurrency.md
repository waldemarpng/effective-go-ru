# Параллельность

[оригинал](https://go.dev/doc/effective_go#concurrency)

## Делиться, общаясь

[оригинал](https://go.dev/doc/effective_go#sharing)

Параллельное программирование — большая тема, и здесь есть место только для нескольких акцентов, специфичных для Go.

Во многих окружениях параллельное программирование затрудняют тонкости правильного доступа к разделяемым переменным. Go поощряет другой подход: разделяемые значения передают по каналам и на самом деле никогда активно не разделяют отдельные потоки выполнения. В любой момент доступ к значению есть только у одной горутины. Гонки данных по замыслу невозможны. Чтобы поощрить такой образ мысли, мы свели его к лозунгу:

> Do not communicate by sharing memory; instead, share memory by communicating.

Не общайтесь, разделяя память; вместо этого разделяйте память через общение.

Этот подход можно завести слишком далеко. Счётчики ссылок, например, лучше делать мьютексом вокруг целой переменной. Но как подход верхнего уровня управление доступом через каналы облегчает написание ясных и корректных программ.

Один способ думать об этой модели — представить типичную однопоточную программу на одном CPU. Ей не нужны примитивы синхронизации. Теперь запустите ещё один такой экземпляр; ему тоже синхронизация не нужна. Теперь пусть эти двое общаются; если общение и есть синхронизатор, другой синхронизации по‑прежнему не нужно. Конвейеры Unix, например, идеально ложатся на эту модель. Хотя подход Go к параллельности восходит к Communicating Sequential Processes (CSP) Хоара, его можно видеть и как типобезопасное обобщение Unix‑каналов.

> **Сейчас.** Для отмены, дедлайнов и значений на всём дереве вызовов есть пакет [`context`](https://pkg.go.dev/context). См. также [Go Concurrency Patterns: Context](https://go.dev/blog/context).

## Горутины

[оригинал](https://go.dev/doc/effective_go#goroutines)

Их называют горутинами, потому что существующие термины — потоки, сопрограммы, процессы и так далее — несут неточные коннотации. У горутины простая модель: это функция, выполняющаяся одновременно с другими горутинами в одном адресном пространстве. Она лёгкая: стоит чуть больше, чем выделение стека. И стеки начинаются маленькими, так что они дёшевы, и растут, выделяя (и освобождая) кучу по мере надобности.

Горутины мультиплексируются на несколько потоков ОС, так что если одна блокируется, например ожидая ввода‑вывода, другие продолжают работать. Их устройство скрывает многие сложности создания и управления потоками.

Поставьте ключевое слово `go` перед вызовом функции или метода, чтобы выполнить вызов в новой горутине. Когда вызов завершится, горутина молча выйдет. (Эффект похож на запись `&` в Unix‑оболочке для запуска команды в фоне.)

```
go list.Sort()  // run list.Sort concurrently; don't wait for it.
```

Литерал функции удобен в вызове горутины.

```
func Announce(message string, delay time.Duration) {
    go func() {
        time.Sleep(delay)
        fmt.Println(message)
    }()  // Note the parentheses - must call the function.
}
```

В Go литералы функций — замыкания: реализация следит, чтобы переменные, на которые ссылается функция, жили, пока они активны.

Эти примеры не слишком практичны, потому что у функций нет способа сигнализировать о завершении. Для этого нужны каналы.

## Каналы

[оригинал](https://go.dev/doc/effective_go#channels)

Как и map, каналы выделяют через `make`, и получившееся значение действует как ссылка на подлежащую структуру данных. Необязательный целый параметр задаёт размер буфера канала. По умолчанию ноль — небуферизованный, или синхронный, канал.

```
ci := make(chan int)            // unbuffered channel of integers
cj := make(chan int, 0)         // unbuffered channel of integers
cs := make(chan *os.File, 100)  // buffered channel of pointers to Files
```

Небуферизованные каналы соединяют общение — обмен значением — с синхронизацией — гарантией, что два вычисления (горутины) находятся в известном состоянии.

Есть много приятных идиом с каналами. Вот одна для начала. В предыдущем разделе мы запустили сортировку в фоне. Канал может позволить запускающей горутине дождаться завершения сортировки.

```
c := make(chan int)  // Allocate a channel.
// Start the sort in a goroutine; when it completes, signal on the channel.
go func() {
    list.Sort()
    c <- 1  // Send a signal; value does not matter.
}()
doSomethingForAWhile()
<-c   // Wait for sort to finish; discard sent value.
```

Приёмники всегда блокируются, пока нет данных. Если канал небуферизован, отправитель блокируется, пока приёмник не получит значение. Если у канала есть буфер, отправитель блокируется только пока значение не скопировано в буфер; если буфер полон, это значит ждать, пока какой‑то приёмник не заберёт значение.

Буферизованный канал можно использовать как семафор, например чтобы ограничить пропускную способность. В этом примере входящие запросы передаются в `handle`, который отправляет значение в канал, обрабатывает запрос, а затем принимает значение из канала, чтобы освободить «семафор» для следующего потребителя. Ёмкость буфера канала ограничивает число одновременных вызовов `process`.

```
var sem = make(chan int, MaxOutstanding)

func handle(r *Request) {
    sem <- 1    // Wait for active queue to drain.
    process(r)  // May take a long time.
    <-sem       // Done; enable next request to run.
}

func Serve(queue chan *Request) {
    for {
        req := <-queue
        go handle(req)  // Don't wait for handle to finish.
    }
}
```

Как только `MaxOutstanding` обработчиков выполняют `process`, остальные блокируются, пытаясь отправить в заполненный буфер канала, пока один из существующих обработчиков не закончит и не примет из буфера.

Однако у этой схемы есть проблема: `Serve` создаёт новую горутину на каждый входящий запрос, хотя в любой момент могут работать только `MaxOutstanding` из них. В результате программа может потребить неограниченные ресурсы, если запросы приходят слишком быстро. Это можно исправить, изменив `Serve` так, чтобы ограничивать создание горутин:

```
func Serve(queue chan *Request) {
    for req := range queue {
        sem <- 1
        go func() {
            process(req)
            <-sem
        }()
    }
}
```

(Заметьте: в версиях Go до 1.22 у этого кода есть ошибка: переменная цикла общая для всех горутин. Подробности — в [Go wiki](https://go.dev/wiki/LoopvarExperiment).)

Другой подход, который хорошо управляет ресурсами, — запустить фиксированное число горутин `handle`, все читающие из канала запросов. Число горутин ограничивает число одновременных вызовов `process`. Эта функция `Serve` также принимает канал, по которому ей скажут выйти; после запуска горутин она блокируется, принимая из этого канала.

```
func handle(queue chan *Request) {
    for r := range queue {
        process(r)
    }
}

func Serve(clientRequests chan *Request, quit chan bool) {
    // Start handlers
    for i := 0; i < MaxOutstanding; i++ {
        go handle(clientRequests)
    }
    <-quit  // Wait to be told to exit.
}
```

## Каналы каналов

[оригинал](https://go.dev/doc/effective_go#chan_of_chan)

Одно из важнейших свойств Go — канал это значение первого класса, которое можно выделять и передавать как любое другое. Обычное применение этого свойства — безопасное параллельное демультиплексирование.

В примере предыдущего раздела `handle` был идеализированным обработчиком запроса, но мы не определили тип, который он обрабатывает. Если в этом типе есть канал, по которому ответить, каждый клиент может предоставить свой путь для ответа. Вот схематическое определение типа `Request`.

```
type Request struct {
    args        []int
    f           func([]int) int
    resultChan  chan int
}
```

Клиент предоставляет функцию и её аргументы, а также канал внутри объекта запроса, по которому получить ответ.

```
func sum(a []int) (s int) {
    for _, v := range a {
        s += v
    }
    return
}

request := &Request{[]int{3, 4, 5}, sum, make(chan int)}
// Send request
clientRequests <- request
// Wait for response.
fmt.Printf("answer: %d\n", <-request.resultChan)
```

На стороне сервера меняется только функция обработчика.

```
func handle(queue chan *Request) {
    for req := range queue {
        req.resultChan <- req.f(req.args)
    }
}
```

Чтобы сделать это реалистичным, явно нужно ещё многое, но этот код — каркас ограниченной по скорости, параллельной, неблокирующей RPC‑системы, и мьютекса в поле зрения нет.

## Распараллеливание

[оригинал](https://go.dev/doc/effective_go#parallel)

Другое применение этих идей — распараллелить вычисление по нескольким ядрам CPU. Если вычисление можно разбить на отдельные куски, которые выполняются независимо, его можно распараллелить, с каналом, который сигнализирует, когда каждый кусок завершился.

Допустим, у нас есть дорогая операция над вектором элементов, и значение операции над каждым элементом независимо, как в этом идеализированном примере.

```
type Vector []float64

// Apply the operation to v[i], v[i+1] ... up to v[n-1].
func (v Vector) DoSome(i, n int, u Vector, c chan int) {
    for ; i < n; i++ {
        v[i] += u.Op(v[i])
    }
    c <- 1    // signal that this piece is done
}
```

Мы запускаем куски независимо в цикле, по одному на CPU. Они могут завершиться в любом порядке, но это неважно; мы просто считаем сигналы завершения, опустошая канал после запуска всех горутин.

```
const numCPU = 4 // number of CPU cores

func (v Vector) DoAll(u Vector) {
    c := make(chan int, numCPU)  // Buffering optional but sensible.
    for i := 0; i < numCPU; i++ {
        go v.DoSome(i*len(v)/numCPU, (i+1)*len(v)/numCPU, u, c)
    }
    // Drain the channel.
    for i := 0; i < numCPU; i++ {
        <-c    // wait for one task to complete
    }
    // All done.
}
```

Вместо того чтобы создавать константу для numCPU, можно спросить runtime, какое значение уместно. Функция `runtime.NumCPU` возвращает число аппаратных ядер CPU в машине, так что можно написать

```
var numCPU = runtime.NumCPU()
```

Есть также функция `runtime.GOMAXPROCS`, которая сообщает (или задаёт) указанное пользователем число ядер, которые программа на Go может иметь выполняющимися одновременно. По умолчанию это значение `runtime.NumCPU`, но его можно переопределить одноимённой переменной окружения оболочки или вызовом функции с положительным числом. Вызов с нулём только запрашивает значение. Поэтому если мы хотим уважить запрос пользователя на ресурсы, стоит написать

```
var numCPU = runtime.GOMAXPROCS(0)
```

Не путайте идеи параллельности (concurrency) — устройства программы как независимо выполняющихся компонент — и параллелизма (parallelism) — выполнения вычислений параллельно ради эффективности на нескольких CPU. Хотя средства параллельности Go могут облегчить устройство некоторых задач как параллельных вычислений, Go — язык параллельности, а не параллелизма, и не все задачи распараллеливания ложатся на модель Go. Обсуждение различия — в докладе, на который ссылается [этот пост в блоге](https://go.dev/blog/waza-talk).

## Дырявый буфер

[оригинал](https://go.dev/doc/effective_go#leaky_buffer)

Средства параллельного программирования могут даже облегчить выражение непараллельных идей. Вот пример, абстрагированный из пакета RPC. Горутина клиента в цикле принимает данные из какого‑то источника, возможно сети. Чтобы не выделять и не освобождать буферы, она держит список свободных и представляет его буферизованным каналом. Если канал пуст, выделяется новый буфер. Когда буфер сообщения готов, его отправляют серверу по `serverChan`.

```
var freeList = make(chan *Buffer, 100)
var serverChan = make(chan *Buffer)

func client() {
    for {
        var b *Buffer
        // Grab a buffer if available; allocate if not.
        select {
        case b = <-freeList:
            // Got one; nothing more to do.
        default:
            // None free, so allocate a new one.
            b = new(Buffer)
        }
        load(b)              // Read next message from the net.
        serverChan <- b      // Send to server.
    }
}
```

Цикл сервера принимает каждое сообщение от клиента, обрабатывает его и возвращает буфер в список свободных.

```
func server() {
    for {
        b := <-serverChan    // Wait for work.
        process(b)
        // Reuse buffer if there's room.
        select {
        case freeList <- b:
            // Buffer on free list; nothing more to do.
        default:
            // Free list full, just carry on.
        }
    }
}
```

Клиент пытается взять буфер из `freeList`; если свободных нет, выделяет новый. Отправка сервера в `freeList` кладёт `b` обратно в список свободных, если список не полон; иначе буфер бросают на пол, чтобы его забрал сборщик мусора. (Ветки `default` в операторах `select` выполняются, когда никакая другая ветка не готова, то есть `select` никогда не блокируются.) Эта реализация строит список свободных по схеме leaky bucket в несколько строк, полагаясь на буферизованный канал и сборщик мусора для учёта.
