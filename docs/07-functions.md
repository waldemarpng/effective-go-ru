## Несколько возвращаемых значений

[оригинал](https://go.dev/doc/effective_go#multiple-returns)

Одна из необычных черт Go — функции и методы могут возвращать несколько значений. Этой формой можно улучшить пару неуклюжих идиом C: возврат ошибки «внутри» значения, вроде `-1` для `EOF`, и изменение аргумента, переданного по адресу.

В C ошибка записи сигнализируется отрицательным числом байт, а код ошибки прячется в изменчивом месте. В Go `Write` может вернуть счётчик и ошибку: «да, вы записали сколько‑то байт, но не все, потому что устройство заполнилось». Сигнатура метода `Write` у файлов из пакета `os`:

```
func (file *File) Write(b []byte) (n int, err error)
```

и, как говорит документация, он возвращает число записанных байт и ненулевую `error`, когда `n` `!=` `len(b)`. Это обычный стиль; больше примеров — в [разделе про ошибки](15-errors.md).

Похожий приём избавляет от нужды передавать указатель на возвращаемое значение, чтобы сымитировать параметр‑ссылку. Вот простоватая функция, которая берёт число из позиции в слайсе байт и возвращает число и следующую позицию.

```
func nextInt(b []byte, i int) (int, int) {
    for ; i < len(b) && !isDigit(b[i]); i++ {
    }
    x := 0
    for ; i < len(b) && isDigit(b[i]); i++ {
        x = x*10 + int(b[i]) - '0'
    }
    return x, i
}
```

Ею можно просканировать числа во входном слайсе `b` так:

```
    for i := 0; i < len(b); {
        x, i = nextInt(b, i)
        fmt.Println(x)
    }
```

## Именованные результаты

[оригинал](https://go.dev/doc/effective_go#named-results)

Возвращаемые, или результирующие, «параметры» функции Go можно именовать и использовать как обычные переменные, как и входящие параметры. Если их именовать, при входе в функцию они инициализируются нулевыми значениями своих типов; если функция выполняет `return` без аргументов, текущие значения результирующих параметров и становятся возвращаемыми.

Имена не обязательны, но могут сделать код короче и яснее: это документация. Если именовать результаты `nextInt`, сразу ясно, какой возвращённый `int` какой.

```
func nextInt(b []byte, pos int) (value, nextPos int) {
```

Поскольку именованные результаты инициализируются и связаны с «голым» `return`, они могут и упростить, и прояснить. Вот версия `io.ReadFull`, которая использует их хорошо:

```
func ReadFull(r Reader, buf []byte) (n int, err error) {
    for len(buf) > 0 && err == nil {
        var nr int
        nr, err = r.Read(buf)
        n += nr
        buf = buf[nr:]
    }
    return
}
```

## Defer

[оригинал](https://go.dev/doc/effective_go#defer)

Оператор `defer` в Go планирует вызов функции (отложенной функции) сразу перед тем, как вернётся функция, выполняющая `defer`. Это необычный, но эффективный способ закрыть ситуации вроде ресурсов, которые нужно освободить независимо от того, каким путём функция возвращается. Канонические примеры — разблокировать мьютекс или закрыть файл.

```
// Contents returns the file's contents as a string.
func Contents(filename string) (string, error) {
    f, err := os.Open(filename)
    if err != nil {
        return "", err
    }
    defer f.Close()  // f.Close will run when we're finished.

    var result []byte
    buf := make([]byte, 100)
    for {
        n, err := f.Read(buf[0:])
        result = append(result, buf[0:n]...) // append is discussed later.
        if err != nil {
            if err == io.EOF {
                break
            }
            return "", err  // f will be closed if we return here.
        }
    }
    return string(result), nil // f will be closed if we return here.
}
```

Отложить вызов функции вроде `Close` выгодно по двум причинам. Во‑первых, вы гарантированно не забудете закрыть файл — ошибка, которую легко сделать, если потом отредактировать функцию и добавить новый путь возврата. Во‑вторых, закрытие стоит рядом с открытием, и это гораздо яснее, чем помещать его в конец функции.

Аргументы отложенной функции (включая получатель, если это метод) вычисляются, когда выполняется `defer`, а не когда выполняется сам вызов. Помимо того что не нужно беспокоиться об изменении переменных по ходу функции, это значит, что одно место `defer` может отложить несколько выполнений функции. Вот глупый пример.

```
for i := 0; i < 5; i++ {
    defer fmt.Printf("%d ", i)
}
```

Отложенные функции выполняются в порядке LIFO, поэтому этот код напечатает `4 3 2 1 0`, когда функция вернётся. Более правдоподобный пример — простой способ трассировать выполнение функций по программе. Можно написать пару простых функций трассировки так:

```
func trace(s string)   { fmt.Println("entering:", s) }
func untrace(s string) { fmt.Println("leaving:", s) }

// Use them like this:
func a() {
    trace("a")
    defer untrace("a")
    // do something....
}
```

Можно лучше, если использовать тот факт, что аргументы отложенных функций вычисляются в момент `defer`. Функция входа может подготовить аргумент для функции выхода. Этот пример:

```
func trace(s string) string {
    fmt.Println("entering:", s)
    return s
}

func un(s string) {
    fmt.Println("leaving:", s)
}

func a() {
    defer un(trace("a"))
    fmt.Println("in a")
}

func b() {
    defer un(trace("b"))
    fmt.Println("in b")
    a()
}

func main() {
    b()
}
```

печатает

```
entering: b
in b
entering: a
in a
leaving: a
leaving: b
```

Программистам, привыкшим к управлению ресурсами на уровне блока в других языках, `defer` может казаться странным, но самые интересные и мощные применения как раз из того, что он привязан не к блоку, а к функции. В разделе про `panic` и `recover` мы увидим ещё один пример его возможностей.
