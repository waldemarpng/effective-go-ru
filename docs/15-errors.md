# Ошибки

[оригинал](https://go.dev/doc/effective_go#errors)

Библиотечные процедуры часто должны вернуть вызывающему какое‑то указание на ошибку. Как уже говорилось, множественный возврат в Go облегчает возврат подробного описания ошибки рядом с обычным значением. Хороший стиль — использовать эту возможность, чтобы дать подробную информацию об ошибке. Например, как мы увидим, `os.Open` при неудаче возвращает не только `nil`‑указатель, но и значение ошибки, описывающее, что пошло не так.

По соглашению ошибки имеют тип `error` — простой встроенный интерфейс.

```
type error interface {
    Error() string
}
```

Автор библиотеки волен реализовать этот интерфейс более богатой моделью под капотом, чтобы можно было не только увидеть ошибку, но и дать контекст. Как сказано, рядом с обычным возвращаемым `*os.File` `os.Open` также возвращает значение ошибки. Если файл открыт успешно, ошибка будет `nil`, а когда есть проблема, в ней будет `os.PathError`:

```
// PathError records an error and the operation and
// file path that caused it.
type PathError struct {
    Op string    // "open", "unlink", etc.
    Path string  // The associated file.
    Err error    // Returned by the system call.
}

func (e *PathError) Error() string {
    return e.Op + " " + e.Path + ": " + e.Err.Error()
}
```

`Error` у `PathError` порождает строку вроде такой:

```
open /etc/passwx: no such file or directory
```

Такая ошибка, которая включает проблемное имя файла, операцию и ошибку операционной системы, полезна даже если её печатают далеко от вызова, который её вызвал; она гораздо информативнее простого «no such file or directory».

Когда возможно, строки ошибок должны указывать своё происхождение, например префиксом с именем операции или пакета, который породил ошибку. Например, в пакете `image` строковое представление ошибки декодирования из‑за неизвестного формата — «image: unknown format».

Вызывающие, которым важны точные детали ошибки, могут использовать type switch или утверждение типа, чтобы искать конкретные ошибки и извлекать подробности. Для `PathError` это может включать проверку внутреннего поля `Err` на восстанавливаемые сбои.

```
for try := 0; try < 2; try++ {
    file, err = os.Create(filename)
    if err == nil {
        return
    }
    if e, ok := err.(*os.PathError); ok && e.Err == syscall.ENOSPC {
        deleteTempFiles()  // Recover some space.
        continue
    }
    return
}
```

Второй `if` здесь — ещё одно утверждение типа. Если оно не удалось, `ok` будет false, а `e` — `nil`. Если удалось, `ok` будет true, значит ошибка была типа `*os.PathError`, и тогда таков же `e`, который можно рассмотреть подробнее.

> **Сейчас.** Чтобы сравнивать и разворачивать ошибки, используйте [`errors`](https://pkg.go.dev/errors) (`Is`, `As`, `Join`) и `fmt.Errorf` с `%w`, а не сравнение указателей и «голые» утверждения типа. См. [Working with Errors in Go 1.13](https://go.dev/blog/go1.13-errors) и [Error handling and Go](https://go.dev/blog/error-handling-and-go).

## Panic

[оригинал](https://go.dev/doc/effective_go#panic)

Обычный способ сообщить об ошибке вызывающему — вернуть `error` как дополнительное возвращаемое значение. Канонический метод `Read` — известный пример; он возвращает число байт и `error`. Но что, если ошибка невосстановима? Иногда программа просто не может продолжать.

Для этого есть встроенная функция `panic`, которая по сути создаёт ошибку времени выполнения и остановит программу (но см. следующий раздел). Функция принимает один аргумент произвольного типа — часто строку — который печатается, когда программа умирает. Это также способ указать, что случилось невозможное, например выход из бесконечного цикла.

```
// A toy implementation of cube root using Newton's method.
func CubeRoot(x float64) float64 {
    z := x/3   // Arbitrary initial value
    for i := 0; i < 1e6; i++ {
        prevz := z
        z -= (z*z*z-x) / (3*z*z)
        if veryClose(z, prevz) {
            return z
        }
    }
    // A million iterations has not converged; something is wrong.
    panic(fmt.Sprintf("CubeRoot(%g) did not converge", x))
}
```

Это только пример, а настоящие библиотечные функции должны избегать `panic`. Если проблему можно скрыть или обойти, всегда лучше дать вещам продолжать работать, чем ронять всю программу. Возможный контрпример — во время инициализации: если библиотека действительно не может себя настроить, паниковать, так сказать, может быть разумно.

```
var user = os.Getenv("USER")

func init() {
    if user == "" {
        panic("no value for $USER")
    }
}
```

## Recover

[оригинал](https://go.dev/doc/effective_go#recover)

Когда вызывают `panic`, в том числе неявно при ошибках времени выполнения вроде выхода индекса слайса за границы или неудачного утверждения типа, немедленно останавливается выполнение текущей функции и начинается размотка стека горутины, по пути выполняя отложенные функции. Если размотка доходит до вершины стека горутины, программа умирает. Однако встроенной функцией `recover` можно вернуть управление горутине и возобновить нормальное выполнение.

Вызов `recover` останавливает размотку и возвращает аргумент, переданный в `panic`. Поскольку во время размотки выполняется только код внутри отложенных функций, `recover` полезен только внутри отложенных функций.

Одно применение `recover` — выключить падающую горутину внутри сервера, не убивая остальные выполняющиеся горутины.

```
func server(workChan <-chan *Work) {
    for work := range workChan {
        go safelyDo(work)
    }
}

func safelyDo(work *Work) {
    defer func() {
        if err := recover(); err != nil {
            log.Println("work failed:", err)
        }
    }()
    do(work)
}
```

В этом примере, если `do(work)` паникует, результат запишется в лог, и горутина чисто выйдет, не тревожа остальных. В отложенном замыкании больше ничего делать не нужно; вызов `recover` полностью обрабатывает условие.

Поскольку `recover` всегда возвращает `nil`, если его вызывают не напрямую из отложенной функции, отложенный код может вызывать библиотечные процедуры, которые сами используют `panic` и `recover`, и не сломается. Например, отложенная функция в `safelyDo` может вызвать функцию логирования до вызова `recover`, и этот код логирования выполнится, не затронутый состоянием паники.

С этим образцом восстановления функция `do` (и всё, что она вызывает) может чисто выйти из любой плохой ситуации, вызвав `panic`. Этой идеей можно упростить обработку ошибок в сложном ПО. Посмотрим идеализированную версию пакета `regexp`, который сообщает об ошибках разбора, вызывая `panic` с локальным типом ошибки. Вот определение `Error`, метод `error` и функция `Compile`.

```
// Error is the type of a parse error; it satisfies the error interface.
type Error string
func (e Error) Error() string {
    return string(e)
}

// error is a method of *Regexp that reports parsing errors by
// panicking with an Error.
func (regexp *Regexp) error(err string) {
    panic(Error(err))
}

// Compile returns a parsed representation of the regular expression.
func Compile(str string) (regexp *Regexp, err error) {
    regexp = new(Regexp)
    // doParse will panic if there is a parse error.
    defer func() {
        if e := recover(); e != nil {
            regexp = nil    // Clear return value.
            err = e.(Error) // Will re-panic if not a parse error.
        }
    }()
    return regexp.doParse(str), nil
}
```

Если `doParse` паникует, блок восстановления выставит возвращаемое значение в `nil` — отложенные функции могут менять именованные результаты. Затем при присваивании `err` он проверит, что проблема была ошибкой разбора, утверждая локальный тип `Error`. Если нет, утверждение типа не удастся, вызвав ошибку времени выполнения, которая продолжит размотку стека, как будто её ничто не прерывало. Эта проверка значит: если случится неожиданное, например выход индекса за границы, код упадёт, хотя мы используем `panic` и `recover` для ошибок разбора.

Когда обработка ошибок на месте, метод `error` (поскольку это метод, привязанный к типу, нормально и даже естественно, что у него то же имя, что у встроенного типа `error`) облегчает сообщение об ошибках разбора без ручной размотки стека разбора:

```
if pos == 0 {
    re.error("'*' illegal at start of expression")
}
```

Хотя этот образец полезен, его стоит использовать только внутри пакета. `Parse` превращает свои внутренние вызовы `panic` в значения `error`; он не выставляет `panic` клиенту. Это хорошее правило.

Кстати, эта идиома повторной паники меняет значение паники, если происходит настоящая ошибка. Однако и исходный, и новый сбой появятся в отчёте о падении, так что корневая причина всё равно будет видна. Поэтому простой подход с повторной паникой обычно достаточен — всё равно это падение, — но если хотите показать только исходное значение, можно написать чуть больше кода, чтобы отфильтровать неожиданные проблемы и запаниковать снова с исходной ошибкой. Это оставляем как упражнение читателю.
